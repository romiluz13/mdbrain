# Live demo

Open `/demo` on the running web app. It walks nine chapters on a synthetic company, Northstar Systems (fictional): the brain as a map, a read-only question, where sources come from, agents at work, a caught contradiction, governed growth, what changed, the reads under the hood, and the pinned run. A "Synthetic company" label stays on screen in every chapter.

Every number and every citation on the page is read from a stored brain through a read-only proxy at `/api/demo/v1`. The page ships no scenario data. A citation opens the stored claim, its evidence and the stored source text, read through `cite`.

A stored source is shown as markdown, drawn as the page's own elements: no HTML in a source reaches the page. Memongo stores an event as a message, so its text opens with a role label such as `User: `; the page shows that apart, as the role the source was stored under, and the text after it as the source. A long source shows the part the claim rests on, highlighted, and the full text behind "Show full source". A claim stored with no evidence says so plainly ("No stored source"), in its chapter and in its citation; a claim that rests only on evidence that is not a source event says that instead. Neither is a loading or a not-yet state.

Chapter 5 is a walk-through of three beats: the first claim, the second claim, and what mdbrain recorded. Buttons, the left and right arrow keys (with focus on a step button) and a tap step it; nothing advances by itself, and a beat eases in only when the person has not asked for reduced motion. On a wide screen the claims stay side by side as the stamp arrives; on a phone each beat is one screen.

## Time

Two clocks are shown apart and always named. **Ingestion time** is when mdbrain stored something (a page's creation and update times, a revision, the moment a contradiction was detected). **Business time** is when a source says something happened (the event's own timestamp, read through `cite`). When a source carries no business time, the page says "missing in this source" rather than showing the ingestion time in its place.

## States

Each chapter shows loading, empty, error and incomplete-run states. A server with no run record configured says "Run not configured" in chapters 3 and 4 and shows what is stored instead; every other chapter keeps working. Chapter 4 has one state for each stage of the agent run, all stated and none an error: no agent run yet ("Not yet in this run"), running, stopped early (a fixed label, never the stored reason), and finished with or without its steps indexed. The governed-growth chapter states that the review queue is private by design: a proposed page is invisible to every wiki read until a reviewer approves it.

## The proxy

The proxy forwards one fixed list of reads and refuses everything else (other methods, writes, admin routes, and any caller-set `scope`, `scopeRef`, `agentId` or `containerTag`). The question read is the only upstream `POST`; the caller still sends a `GET` with a bounded `query` and the proxy builds the whole upstream body (text lane, no model). Configure it with server environment variables, none of which reaches the browser:

| Variable | Meaning |
|---|---|
| `MDBRAIN_DEMO_API_BASE_URL` | The Mdbrain API to read from |
| `MDBRAIN_DEMO_READ_KEY` | A read-only key the proxy sends upstream. On the local demo stack it is slot i's entry in `MDBRAIN_DEMO_READ_KEYS`: read capability only, granted exactly that slot's scope (`scripts/demo-stack-config.ts`) |
| `MDBRAIN_DEMO_SCOPE_REF` | The pinned run's scope reference |
| `MDBRAIN_DEMO_AGENT_ID` | The agent the pinned run's events were written under, `demo-run-<slot>` for a seeded slot |
| `MDBRAIN_DEMO_SCOPE` | The scope, default `workspace` |
| `MDBRAIN_DEMO_CONTROL_URI` | The demo control database's connection string, for the run read only (see below) |
| `MDBRAIN_DEMO_RUN_ID` | The pinned run's id: the `_id` of its stored record, as the seeding driver named it (for example `live-check-b-2026-10-20T11-29-54.742Z`). It is not the scope reference or the agent id |

Without the first four the route answers `503 PROXY_NOT_CONFIGURED`. The scope reference and the agent id must match `[A-Za-z0-9_-]{1,128}`; the run id may also hold `.` and `:`. The last two are optional: without either, the run read answers `503 RUN_NOT_CONFIGURED` and nothing else changes.

An event citation (`GET /v1/cite` with an `[[event:ID]]` marker) resolves the event by its id in the pinned scope, as the request's agent, whether or not a stored claim cites it. Every demo event lives under the run's own agent, so without `MDBRAIN_DEMO_AGENT_ID` no event citation resolves (`404 CITATION_UNRESOLVED`). The browser may add `citedBy`, a stored claim's marker; the claim must then list the event, or the cite is unresolved. The proxy sends the agent on the `cite` read only: no other read uses it, so sending it elsewhere would only widen what the key's grant must allow. A caller-set `agentId` is still refused.

Errors have one public shape, `{"error": {"code", "message"}}`, built by the proxy. When the upstream fails or cannot be reached, no transport message, no upstream message text and no other upstream field reaches the browser: they can name hosts, paths, scopes and stored page titles. Five upstream codes keep their code and get a fixed message (`WIKI_NOT_FOUND` 404, `CITATION_NOT_FOUND` 404, `CITATION_UNRESOLVED` 404, `SEARCH_UNAVAILABLE` 503, `RATE_LIMITED` 429). Anything else, `CITATION_LOOKUP_FAILED` among it, becomes `502 UPSTREAM_ERROR`, and an unreachable upstream, or one whose answer fails while its body is read, `502 UPSTREAM_UNREACHABLE`, each with a fixed message. The page reads the code for one thing: a source the API cannot confirm (`CITATION_UNRESOLVED`, `CITATION_NOT_FOUND`) is said to be unconfirmed, apart from one that could not be read. A source that could not be read is asked for again the next time it is opened. Successful reads pass through unchanged, with the read key redacted.

## The run read

The run's own record (which source files arrived and in what order, what its agents did) is not an API route: the seeding driver keeps it in the demo control database, `mdbrain_demo_control.demo_run_manifests`. The proxy serves it at one more fixed read, answered by the web server:

- `GET /api/demo/v1/run` takes no parameter. The server does one `findOne({_id: MDBRAIN_DEMO_RUN_ID})` and answers a public projection: the run's state, its timestamps, the planned and written counts, its arrivals as `{sourceId, eventId}` in the order they were written, the pages written, and the agent run (state, timing, token usage, the page it reused, the proposal it left pending, and its steps when they were indexed). It carries no run id, scope, agent, corpus digest or replay list, and never the text of a failure: a run that stopped gets a fixed label. A record whose `scopeRef` or `agentId` differs from the pinned ones is refused (`502 RUN_RECORD_MISMATCH`); one that does not have the stored shape is `502 RUN_RECORD_MALFORMED`; an unreachable database is `502 RUN_UNREACHABLE`; a missing record is `404 RUN_NOT_FOUND`. The connection string never reaches the browser, a log or an error body.

The record names the event behind each arrival and each step; the page confirms each through `cite`, not through the run read.

The web server holds one `MongoClient` for the control database, on `globalThis` under a fixed key, so a dev reload that re-evaluates the route does not orphan a pool and every request shares it. It never calls `connect()` itself: the driver connects on the first operation, a failed connection is retried by the next one, and the pool is capped at five. The run read is built for the Node server (`next start`, the Docker image); it has not been exercised on the Cloudflare Workers build.

Chapter 3 lists the arrivals in the record's order, ten at first and ten more on request, and labels the counts "the run's record". Each shown arrival is confirmed by its id through `cite`, so an arrival no stored claim cites is confirmed all the same; its row says "No stored claim cites it" and has no "Open source" button, since that opens the citing claim. An arrival the API cannot confirm says so and is tallied apart from the confirmed ones. Chapter 4 reads the agent run: three roles in hand-off order, wall time, tokens against the 150,000 ceiling, the reused page and its revision through a wiki read, the proposal's absence from the wiki as the expected state of a pending proposal, and each role's steps, confirmed by their event ids through `cite` when its steps are opened. Every arrival and step is confirmed through the one function `confirmEvent` (`apps/web/lib/demo-data/confirm-event.ts`), so a different way to confirm is a change to that function alone.

Code: the allowlist, the env and `handleDemoRead` are in `apps/web/lib/demo-data/proxy.ts`; the run paths are in `proxy-run.ts`, their projection in `run-record.ts` and the database read in `run-store.ts`; the route table, parameter specs and slug checks are in `proxy-routes.ts`; the error envelope is `proxy-errors.ts`.

## Tests

`bun run test:e2e` runs the journey (`e2e/demo.e2e.ts`) and the value, state, quality and walk-through checks (`e2e/demo-values.e2e.ts`, `e2e/demo-states.e2e.ts`, `e2e/demo-checks.e2e.ts`, `e2e/demo-stepper.e2e.ts`) on the desktop and mobile projects. By default the page reads a fixture upstream built from the committed Northstar corpus (`e2e/demo-upstream.ts`) and served through the real proxy handler, so the allowlist, the server-set principal and the read key are exercised. The fixture's run (`e2e/demo-run.ts`) is a stored record in the control database's shape, behind the real run handler, and the events its steps wrote, which the fixture API cites by id like every corpus event; `e2e/demo-run.e2e.ts` holds chapters 3 and 4 to it in every state (`run: {variant}`: finished with steps, finished without, none yet, running, stopped early, not configured; `missedSteps` for a step whose event the API cannot resolve). A recording replays the run it recorded, and a recording made before the run read replays as "Run not configured". The fixture carries the shapes a live stack has (Memongo UUID event ids, a role label on event text, a changes feed of several pages, an event cite that needs the run's agent), a run with no contradiction yet (`contradiction: "none"`), and a contradiction whose second claim is stored with no evidence (`"unsourced"`); it is not a recording of a live stack. To run the same specs against a live stack, start the web app with the `MDBRAIN_DEMO_*` variables set and run with `DEMO_E2E_LIVE=1`; the comparisons of on-screen values with the proxy's responses then read the live responses, while the tests that force states (outage, empty run, a source without business time) are skipped. A live test is allowed 180 s instead of 30 s, and a list of sources (chapter 3, a citation, a role's steps) is waited on for up to 90 s because it is read four at a time; these were set for a slower cite and have not been measured against the by-id read. Live, the API can refuse a cite: a source it cannot confirm shows as an unavailable slip that says the API could not confirm it, and a failed read says it could not be read right now. A source the proxy refused is held to that, and the browser's one "Failed to load resource" console line for it is accounted for by the refused read; any other console or page error still fails the journey, and the fixture refusing a read fails it too. Chapter 5 branches on the proxy's own lint answer: a run before its agent run must show the honest "not recorded in this run yet" state, and a run with a contradiction must show the walk-through, each claim holding to its evidence count.

`e2e/demo-record.e2e.ts` records the reads `/demo` makes into a JSON file with no key, origin or principal in it (`DEMO_RECORD_TO=<file>`, run through the recorder script a maintainer owns), and `DEMO_REPLAY=<file>` serves that file in place of the generated fixture.

Two specs run only on demand: `e2e/demo-perf.e2e.ts` (`DEMO_PERF=1` and `--workers=1`, ready time on the throttled phone profile against a production server, with the proxy reads modelled on the link: a round trip each, then the gzipped body on a shared 9 Mbit/s downlink) and `e2e/demo-shots.e2e.ts` (`DEMO_SHOTS_DIR=<dir>`, a screenshot of every chapter on both projects).
